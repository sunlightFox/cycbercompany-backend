# 执行意图路由

## 目标

用户的一句话不应靠关键词猜测为“聊天”或“操作本机”。系统需要在创建 Run 前确定一个可审计的
执行姿态，并且在不确定时要求澄清，不能静默降级为普通对话。

## 决策顺序

```text
显式 UI/API 执行目标
  -> 已授权节点 / 本机执行器
  -> 模型结构化意图分类
  -> CHAT | LOCAL_EXECUTION | CLARIFY
  -> 工具发现、权限交集、审批和执行
```

1. `nodeId` 或节点标签由用户明确提交时，服务端保留该选择。模型不能改写目标。
2. 没有显式目标时，控制面调用当前选定模型进行严格 JSON 分类。模型只能从三种姿态中选择，
   不能返回路径、命令、节点 ID 或工具名。
3. `LOCAL_EXECUTION` 仅将 Run 绑定到已经存在的 `in-process-local` 执行器；它不增加工具、
   文件、Shell 或生产权限。
4. 无法解析或置信度低于 `0.75` 时，返回 `422 EXECUTION_TARGET_CLARIFICATION_REQUIRED`。模型故障时，
   仅明显非动作请求使用保守聊天降级；任何可能有副作用的请求仍返回 422。客户端应显示“在此电脑执行”
   与“仅聊天”的选择，随后带着显式 `nodeId` 重发请求。
5. 决策写入 `RunSpec` 和策略摘要，重试、审计和故障诊断均使用原始快照，不重新推断。

## 模型提示边界

模型分类的输入只有路由任务和用户消息，输出使用固定 JSON：

```json
{"intent":"CHAT|LOCAL_EXECUTION|CLARIFY","confidence":0.0,"reason":"short explanation"}
```

它无法授予权限。最终可调用工具仍是 Run 请求、Agent allow-list、节点能力、服务端策略与审批的交集。
URL、IP、网页内容和上传文件不是执行授权；“部署到某台服务器”也不会被误认为本机。

## 前端合同

客户端应始终提供可见的执行目标选择，而不是依赖模型猜测：

- `仅聊天`：不提交 `nodeId`；
- `在此电脑执行`：提交 `nodeId: "in-process-local"`；
- `指定节点`：提交用户已选择的节点 ID；
- `受信沙箱`：提交 `nodeId: "auto"` 或显式节点标签。

当 API 返回 422 时，客户端使用响应的 `decision` 解释原因，并保留原始输入等待用户确认。
