# ADR-0005：采用“后端控制中心 + 节点执行器”实现电脑和服务器操作

- 状态：Accepted
- 日期：2026-07-30

## 背景

项目已经具备模型管理、Skill 管理、MCP 管理、联网搜索和知识库 RAG 等基础能力。下一步如果要让 Agent 真正完成项目编程、整理文件、操作浏览器、执行服务器命令，不能简单地让后端进程直接拥有所有机器权限。

需要一种既能操作本机资源，又能保持权限边界、审计记录和多设备扩展能力的架构。

## 决策

采用“CycberCompany 后端控制中心 + 独立节点客户端”的架构。

- 后端继续使用 Spring Boot；
- 后端新增 `node` 模块，负责节点注册、认证、在线状态、能力声明、工具管理、策略校验、任务下发和审计；
- 节点客户端第一版使用 Java 21；
- 节点通过 WebSocket 主动连接后端；
- 节点工具协议采用 JSON-RPC 风格消息；
- 浏览器自动化第一版使用 Playwright；
- shell、文件、git、browser 均作为节点工具暴露；
- 工具需要支持节点级启用、工具级启用、路径白名单、高风险审批。

## 备选方案

### 方案一：后端直接执行本地命令

优点：

- 实现最快；
- 不需要额外节点客户端。

缺点：

- 只能操作后端所在机器；
- 云端部署时无法访问用户电脑；
- 权限风险集中在后端；
- 不适合多设备、多服务器、多用户场景。

结论：不采用。

### 方案二：所有任务都放到云端沙箱

优点：

- 隔离性好；
- 环境可复制；
- 适合运行不可信代码。

缺点：

- 无法访问用户本机项目、桌面、浏览器登录态；
- 成本更高；
- 对内网服务器操作不方便。

结论：作为后续可选节点类型，不作为第一版主路径。

### 方案三：后端控制中心 + 节点执行器

优点：

- 支持用户电脑、内网服务器、云端沙箱同时接入；
- 节点主动连接后端，穿透 NAT 更容易；
- 本地资源留在本地；
- 后端可以统一做权限、审计和编排；
- 能渐进支持 shell、文件、git、浏览器、MCP、桌面自动化。

缺点：

- 需要维护节点客户端；
- 协议和断线重连要设计好；
- 安全策略复杂度更高。

结论：采用。

## 后果

正面：

- 项目具备演进为“真实 Agent 工作台”的基础；
- 后端不再局限于自己所在机器；
- 节点能力可以按机器差异动态声明；
- 后端现有 ToolCatalog、RunEvent、MCP、Skill 能力可以复用；
- 浏览器和项目代码操作能在用户本机完成。

负面：

- 需要新增节点客户端工程；
- 第一版要投入通信、认证、心跳、重连、审批、审计等基础设施；
- 对 Windows/macOS/Linux 的路径和 shell 差异要做适配。

## 实现顺序

1. 后端 `node` 模块：注册、列表、在线状态；
2. 节点客户端：register、WebSocket、心跳；
3. 节点工具声明和启用/禁用；
4. 文件系统工具；
5. shell 和 git 工具；
6. Playwright 浏览器工具；
7. 接入 ToolCatalog 和 Agent Run；
8. 高风险操作审批；
9. 节点执行日志页面。
